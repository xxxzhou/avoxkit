# M2 功能规划(2026-11-01)

> 本文是 M2 的**取舍决策**, 不是实现口径。每批开工前另出 kickoff 文档;
> 跨仓接口(avox 缺口)按惯例先出接口设计、对齐后再写码。
> 用户功能边界以 `docs/features.md` 为准; 架构术语见 `docs/functional-architecture.md` §2.1/§7。

## 0. 依据

2026-11 用三个调研 agent 覆盖英文社区(GitHub/Stack Exchange/Reddit)、中文社区
(V2EX/吾爱破解/小众软件/知乎)、竞品功能请求渠道, 约 90 次抓取。交叉验证出的
「高需求 × 低供给」缺口, 与本仓现状对照:

| 调研结论 | 本仓现状 | 结论 |
|---|---|---|
| 提取音频高频 | 已有(extract) | 保持 |
| 字幕提取/本地识别需求大 | 已有(subtitle, SenseVoice) | 烧录/翻译缺失 |
| 无损剪切证据最强(LC #126 120👍, SO 1.2M 浏览) | 截取页全重编码, 起点吸关键帧 | **旗舰新增** |
| 批量/队列可靠性(HandBrake >30 项崩、>500 项极慢) | TaskGroup 已有, 队列仅内存、重启即失 | **重点完善** |
| 免费/本地/无账号是结构性空位 | 本仓定位即此 | 定位验证, 不新增 |
| 压缩到目标大小(微信 25MB 场景) | 无 | 低成本新增 |
| 无损合并(SO 1.24M 浏览, 全站最高) | 无 | 新增 |
| 外部音轨导入/替换(HandBrake #871 62👍, 十年未做) | 无 | 新增(纯 shim) |
| 本地视频修复免费端真空(付费墙产品霸市) | 无 | 第二批新增 |
| GIF/静音剪切/旋转元数据/AV1 软编 | 无 | 备选池, 不承诺 |

## 1. 优先级总览

**完善(现有功能):** 队列可靠性 → 预设系统 → 转换页目标大小 → UI 缺口(拖拽/字体/P2 清单)

**新增(按序):** ① 无损剪切(smart cut) ② 字幕烧录 ③ 无损合并 ④ 音轨导入/替换
⑤ 视频修复 v1 ⑥ 字幕翻译

节奏: 先发 0.1.0(提审前置=截图+AGPL 源决策, 不被 M2 阻塞); M2a 与发布收尾并行,
M2b 的 avox 接口设计可先行, 实现、发版后全面铺开。

## 2. 关键决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 旗舰=无损剪切, 落在截取页加「无损」档: 先关键帧精确(即时出片), 再 smart cut(切点小段重编+中间流拷贝, 帧精确) | 证据最强且竞品承认做不完(LC #126 作者原话「关键帧之间没法切」); Bandicut 收费证明付费意愿; functional-architecture §7 #9 本就预留, 等 avox M4。截取页区间尺/关键帧刻度已建, 只加输出档位 |
| D2 | 字幕烧录作为第二个引擎缺口, 走 transcode 加 filter stage, 样式可控(字体/字号/描边/底色/位置) | pyVideoTrans 19.6k star + 剪映把字幕翻译划进 SVIP 空出的需求; 与已有提取/识别闭环成「提取→识别→烧录」一条线; functional-architecture §7 #8 |
| D3 | 队列可靠性是 M2 完善主线: 队列与历史落盘、重启后未完成任务可重新排队(不假装续跑)、完成后动作(通知/睡眠/关机)、千级任务 UI 虚拟化 | HandBrake 队列痛点(>30 崩、>500 慢、不吃设置)是口碑级槽点; 本仓队列 v0 仅内存, 是当前最大可靠性短板; DataHoarder 转库场景需要「跑完关机」 |
| D4 | 目标大小模式进转换页: 输入目标 MB, 两遍编码自动算码率, 音频能直拷先直拷 | 成本极低(R+P, §7 #2, 零 shim 改动); 微信 25MB 是中文特有高频场景, 现有解法全是改后缀/分卷 hack |
| D5 | 无损合并 = 新工具页, remux 族; 参数一致才直拷拼接, 不一致给出明确差异与「先统一转码再合并」可选路径, 不偷偷转码 | SO 全站最高浏览(1.24M); concat 要求编码参数一致是普通用户踩坑点; 与转换页「自动判定+明确提示」口径一致 |
| D6 | 音轨导入/替换进 remux 族(select_tracks 复用), shim 侧可闭环, 不等 avox | HandBrake #871 十年 62👍 未做, 是「转码器/封装器中间地带」; 本仓架构零 ABI 即可做(§7 #19) |
| D7 | 视频修复 v1 只承诺「remux 可救的范围」: 断尾/索引损坏的重封装修复; 参照文件重建 moov 留 v2, 明确不可修范围不上 UI | 三源交叉验证的免费端真空; 商业竞品(牛学长/Repairit)按焦虑定价且有未加密存储丑闻; 但可修范围有限, 按文案红线只写真实能力 |
| D8 | 字幕翻译按既定形态走: 配置进设置、analyze 族、内嵌字幕翻译, 不建一级 AI 区 | 已定案(LLM 形态决策); pyVideoTrans 的「识别→翻译→烧录」闭环里我们已有识别, M2b 补烧录后翻译是最后一块 |

## 3. 分期与完成定义

### M2a 完善批(零 shim/引擎改动, 可与 0.1.0 并行)

| 项 | DoD |
|---|---|
| 队列落盘与恢复 | 重启后队列与历史可见; 未完成任务标记中断、可一键重新排队; 不残留假「进行中」 |
| 完成后动作 | 组级「完成后通知/睡眠/关机」; 关机前确认产物落盘 |
| 大批量性能 | 1000+ 任务提交与列表滚动不卡(虚拟化); 批量组统计准确 |
| 预设系统 | 工具页可保存/命名/应用/删除预设; 出厂预设: 微信 25MB、H.265 省空间、1080p 通用 |
| 目标大小模式 | 转换页输入目标 MB → 自动两遍编码; 完成体积偏差过大时明确提示 |
| UI 缺口收尾 | 文件拖拽入队; 界面字体方案; UI 评审 P2 清单继续清 |

### M2b 旗舰批(avox 接口先行, design-first)

| 项 | 依赖 | DoD |
|---|---|---|
| 无损剪切·关键帧档 | avox 无损剪切 API(M4) | 截取页选「无损」: 起止落关键帧、秒级出片、流不重编; 时间戳连续可播 |
| 无损剪切·smart cut | 同上 | 帧精确切点: 边界 GOP 小段重编、中间流拷贝; 音画同步(长 GOP H.264/H.265 验证); 失败自动回退关键帧档并说明 |
| 字幕烧录 | avox 字幕烧录 stage | SRT/ASS 烧录, 样式可控; 接受提取/识别产出的 srt; 批量可用 |
| 无损合并 | avox concat | 多文件排序合并; 参数一致直拷; 不一致列出差异项, 可选「先统一转码再合并」 |
| 音轨导入/替换 | 无(纯 shim) | 外部音频封装为新轨(可保留/替换原轨), 不重编视频; 容器不支持时明确提示 |

### M2c 第二批(视 M2b 进度定优先序)

| 项 | 依赖 | 说明 |
|---|---|---|
| 视频修复 v1 | avox 宽松读取/remux | 断尾/索引损坏重封装; 明示可修范围与失败原因 |
| 字幕翻译 | LLM 配置形态已定 | 内嵌字幕 + srt 翻译, 配置进设置 |

### M3 备选池(不承诺, 按信号再排)

抽帧/封面(§7 #13, 纯 shim)、GIF/WebP(§7 #14)、旋转/元数据无损编辑
(LC #643, HandBrake #3588 47👍)、响度归一化(§7 #18)、AV1 软编预设(需 kit 加
SVT-AV1; 硬件 AV1 先靠现有硬编探测)、修复 v2(参照文件重建 moov)。

## 4. 明确不做

- **站点解析/无水印下载**: 输入来源已定案(本地/NAS/URL 直链); 调研显示这是全场
  最大原始需求(52pojie 单帖 4.6 万浏览)但工具死亡率 100%, 死因是平台对抗+法律风险。
- **视频去水印**: 需求真实但效果预期不可控(移动水印基本无解), 保留图像修复即可;
  若未来做, 也只承诺「固定位置遮挡/裁切」级别并写清边界。
- **多轨剪辑/创作向功能**: 定位红线。

## 5. 风险

| 风险 | 对策 |
|---|---|
| smart cut 音画对齐是硬工程(LC #126 评论区全是失步案例) | avox 接口设计先把时间戳/重采样对齐责任划清; 失败回退关键帧档, 宁可慢一档不出错片 |
| 烧录样式跨格式差异大(ASS 与 SRT 能力不对等) | 样式面板按字幕格式分级展示; 不支持项不显示, 不造假控件 |
| 修复类功能用户预期过高 | 文案只写「可修范围」; 修不了时给出明确原因, 不做假进度 |
| 队列落盘引入跨版本 schema 问题 | 落盘格式带版本号; 只做「重新排队」不做「续跑」, 避开断点状态一致性 |
